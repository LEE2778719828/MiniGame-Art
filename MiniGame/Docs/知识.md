## 当前正确链路（先记住这张图）

```
SK_Hero（骨骼网格，带 UV、两个材质槽）
    │  使用骨架
    ▼
SK_Hero_Skeleton（53 根骨头 + RightHand 上的 KnifeSocket）
    │  动画 / ABP 都绑在这份骨架上
    ▼

SK_Hero 槽 0  blinn3_002          ──┐
SK_Hero 槽 1  pasted__blinn3_002  ──┴─► MI_HeroSkin
                                           ├─ Parent = M_muban（着色算法）
                                           ├─ Tex    = T_HeroSkin（2048 皮肤图集）
                                           └─ 整体亮度 = 4.0
```

引擎路径：

| 资产 | 路径 |
|---|---|
| 网格 | `/Game/Night/Character/SK_Hero` |
| 骨架 | `/Game/Night/Character/SK_Hero_Skeleton` |

## 1. 贴图从哪来，是不是 FBX 里那张「对的图」

**短答：网格来自动画 FBX；能看的皮肤图不是 FBX 自带的那套灰材质，而是后来换上的 `T_HeroSkin`。**

### 1.1 FBX 导入时带进来的是什么

`SK_Hero` 从 `ArtSubmit/Character/mini_zhujue/anim/Slash_fast.fbx` 导入（见 §8）。FBX 里有：

- 带蒙皮的人（顶点、三角面、UV）
- 两个 Maya 材质名：`blinn3_002`、`pasted__blinn3_002` → 变成网格上的两个槽
- 默认的 blinn 着色（导入后往往是灰的）

FBX **不等于**美术给的皮肤图集。Maya/Blender 的默认材质只是占位。导入时如果勾了「导入材质/贴图」，引擎会在 `Night/Character` 下再造 `blinn3_002` 这类材质资产，那是灰的占位，不是现在身上的皮。

### 1.2 第一次换图：换错了图集（人还是灰的）

当时仓库里已有给 **R2 静态模 `kat`** 用的图：`T_Hero` / 后来的 `T_HeroBase`（从 `kat_base_color.jpg` 降到 2048 导入）。

`SK_Hero` 的 UV 对不上那张图集。逐像素比对过，翻转/旋转都对不上。UV 采样落到白区和灰区，看起来像「没贴上」，其实是**贴错了**。

| 错的 | 对的 |
|---|---|
| `T_Hero` / `T_HeroBase` + `MI_HeroSkel` / `MI_HeroTexture`（kat / `M_NightTexture`） | `T_zhujue1` 的像素 → `T_HeroSkin` + `MI_HeroSkin`（`M_muban`） |

`T_HeroBase`、`MI_HeroSkel` 现在还在 `Night/Character` 里，是旧实验残留，**不要再挂到 `SK_Hero` 上**。

### 1.3 第二次换图：现在这张皮

从正式资源 `T_zhujue1` 拷像素到 `Content/Night/Character/T_HeroSkin`，再新建 `MI_HeroSkin` 挂到两个槽。

网格还是 FBX 那份，换的是**贴图资产和材质实例**，没有重导 FBX。

`T_HeroSkin` 的「源文件」记录现在可能是本机路径，例如：

`E:/腾讯gamejam/微信图片_20260818180604_231_395.png`

这只是导入器记下的磁盘备注（见 §5），不是「皮肤来自微信」。游戏引用的永远是 `/Game/Night/Character/T_HeroSkin`。

### 1.4 和美术正式网格是不是同一个东西

`zhujue.fbx`（`ArtSubmit` 里跟 `anim/` 同级的那份）**一根骨头都没有**，只有 `kat` / `maozi` / `beidai` 等网格节点，不能当骨骼主角。

美术工程里的 `SKM_zhujue` 实际来自 `anim/Sitting.fbx` 一类动画导出。我们的 `SK_Hero` 来自同场景的 `Slash_fast.fbx`。包围盒相同（约 27.3 / 78.1 / 104.2），几何同源。`pasted__` 双槽两边都有。所以**不必把 `SKM_zhujue` 换过来**，也不用做动画 Retarget。

## 2. 纹理、材质、材质实例

可以记成：**贴图是布料，材质是缝纫图纸，材质实例是按图纸做好、只换布料和松紧的成衣。**

### 2.1 贴图（Texture，`T_`）

就是一张图。引擎只存像素，不管它「像衣服还是像脸」。

`T_HeroSkin`：2048×2048，sRGB。模型用 UV（面上的二维坐标）去这张图上取样，把颜色贴到三角面上。

贴图自己不会做卡通风光照，也不会乘亮度。那是材质干的。

### 2.2 材质（Material，`M_`）

一张**计算图纸**：节点图。改节点 = 改算法，所有孩子一起变。

`M_muban` 大约 29 个节点，对外露出的旋钮主要是：

- **`Tex`**：可换的贴图口（母材质默认图是 `T_muban1`，木板用的，所以叫 muban）
- **`整体亮度`**：标量，默认 1
- 一套按法线 / 天光切暗面亮面的卡通风光照

打开 `M_muban` 看到的是节点图。角色、木板、不少道具都共用这套规矩。

### 2.3 材质实例（Material Instance，`MI_`）

不画节点。只说：「用哪张父材质，旋钮拧到多少。」

`MI_HeroSkin` 现在：

| 参数 | 值 |
|---|---|
| Parent | `M_muban` |
| `Tex` | `T_HeroSkin` |
| `整体亮度` | `4.0`（图偏暗，乘 4 才接近该有的白天观感） |

模型槽上挂的是 **MI**，不是裸贴图，也很少直接挂母材质。网格问的是「表面怎么着色」，答案是整套材质；贴图只是其中一个输入。

换肤通常只改 MI 的 `Tex`，不用重画 `M_muban`。

### 2.4 为什么 Parent 必须是 `M_muban`

不是因为主角是木板。`muban` 是美术工程里那套**通用表面材质**的名字。

`MI_zhujue` 的 Parent 也是 `M_muban`。我们要同一套光照和同一套参数口，所以 HeroSkin 必须认同一个妈。

如果改成引擎默认材质：

- 往往没有 `Tex` 这个口，或采样方式和 UV 对不上
- 没有那套分阶光照，人会突然变「写实塑料感」
- 亮度口也对不上

## 3. `MI_HeroSkin` 是不是复制的 `MI_zhujue`

**不是。** 它们是**姐弟**：同一个父材质，两份独立实例。

| | `MI_zhujue`（美术原件） | `MI_HeroSkin`（我们新建的） |
|---|---|---|
| 路径 | `/Game/新建文件夹/模型和材质/材质实例/` | `/Game/Night/Character/` |
| Parent | `M_muban` | `M_muban` |
| `Tex` | `T_zhujue1` | `T_HeroSkin` |
| 亮度 | 4.0 | 4.0 |

当初**故意不 Duplicate** `MI_zhujue`：复制实例会把 `T_zhujue1` 的路径写死进文件，改参数也清不干净。那张图当时还在未跟踪的中文目录里，带着提交别人会缺资产。

实际做法：

1. 把 `T_zhujue1` **拷像素**成 `T_HeroSkin`（贴图是复制的）
2. **从零新建** `MI_HeroSkin`，Parent 指到 `M_muban`
3. 把 `Tex`、亮度拧成和 `MI_zhujue` 一样的观感
4. 挂到 `SK_Hero` 两个槽上

`MI_HeroSkin` 的依赖里只有 `M_muban` 和 `T_HeroSkin`，没有 `MI_zhujue`。

以后要新实例：右键 `M_muban` → **Create Material Instance**，再设 `Tex`。不要 Duplicate `MI_zhujue`。

## 4. 自己怎么换贴图

模型槽上挂的是材质实例，不是贴图。换肤 = 换实例里那张图。两个槽都挂着同一个 `MI_HeroSkin`，改一次两边一起变。

### 4.1 只换一张新图（最常见）

1. 把 png/jpg 拖进 Content Browser，放到 `Content/Night/Character/`，例如 `T_HeroSkin_New`
2. 双击 **`MI_HeroSkin`**（不是 `SK_Hero`）
3. 参数 **`Tex`** 拖成新贴图
4. `Ctrl+S`

### 4.2 覆盖现在这张 `T_HeroSkin`（文件名不变）

见 §5。覆盖或换源之后，`Tex` 不用改。

### 4.3 不要做的事

- 不要把贴图直接拖到 `SK_Hero` 的槽上（槽要材质/实例）
- 不要把 `T_HeroBase` / `MI_HeroTexture` / `MI_HeroSkel` 塞给骨骼主角
- 不要 Duplicate `MI_zhujue` 再改参数
- 不要指望改 `BP_NightHero.HeroMaterial` 来换骨骼皮肤（C++ 已不再用它刷骨骼；静态模路径仍会用）

亮度不对：拧 `MI_HeroSkin` 的 **`整体亮度`**（现在是 4）。

在编辑器里对一下手：

1. 双击 `M_muban` → 节点图（图纸）
2. 双击 `MI_HeroSkin` → 没有节点，只有参数
3. 双击 `T_HeroSkin` → 只有一张图
4. 双击 `SK_Hero` → Material Slots 里是 `MI_HeroSkin`

## 5. 重新导入 vs 用新文件重新导入

两个都是「刷新这一个已有的 `.uasset`」，不是新建资产。差在：源文件还用原来那条路径，还是换成另一份文件。

以 `T_HeroSkin` 为例。资产里存两样东西：

- 引擎里的 2048 像素（游戏真正用的）
- 一句备注：「我是从磁盘哪份文件灌进来的」

你看到的源文件：

`E:/腾讯gamejam/微信图片_20260818180604_231_395.png`

就是这句备注。`MI_HeroSkin.Tex` 指的是 `T_HeroSkin`，不指 E 盘。

这台机器上该路径曾经找不到文件。用这件事对照最清楚。

### 5.1 重新导入（Reimport）

只做一件事：再去读**已经记下的那条路径**。

- 微信那张 png 还在 E 盘原处，且你用同名同路径覆盖过 → 像素更新，资产还叫 `T_HeroSkin`，`MI_HeroSkin` 不用改
- 文件不在 / 路径变了 → 失败或提示找不到源。身上的皮不变

它**不会**让你选别的图。

### 5.2 用新文件重新导入（Reimport With New File）

弹出选文件。例如选 `D:\美术新交\zhujue_skin_v2.png`，然后：

1. 用新图覆盖 `T_HeroSkin` 里的像素（名字路径都不变）
2. 把源文件记录改成新路径

之后 Details 里不再写微信那张图。再点「重新导入」，就会去读新路径。`Tex` 仍然不用改。

### 5.3 和「拖一张新图进 Content」不是一回事

| 操作 | 引擎里发生什么 | `MI_HeroSkin` 要不要改 |
|---|---|---|
| 重新导入 | 还是 `T_HeroSkin`，像素更新 | 不用 |
| 用新文件重新导入 | 还是 `T_HeroSkin`，像素更新，源路径换成新文件 | 不用 |
| 把新 png 拖进 Content | **多出一个** `T_HeroSkin_New` | 要把 `Tex` 指到新资产 |

### 5.4 对网格 / FBX 也一样，但更危险

`SK_Hero` 上 Reimport 会按旧 FBX 路径刷新网格；Reimport With New File 是换一个 FBX 灌进**同一个** `SK_Hero`。动画绑定、材质槽名字可能被导入选项冲掉。换主角网格更稳妥的是另导一份新 SK，不要拿新 FBX 直接盖 `SK_Hero`。贴图相对安全。

### 5.5 日常怎么选

| 手头情况 | 用哪个 |
|---|---|
| 源 png 还在原路径，只是画过一版 | 覆盖原文件，再点**重新导入** |
| 源文件没了，或新图在别处、叫别的名字 | **用新文件重新导入** |
| 想留着 `T_HeroSkin` 不动做对比 | 拖进 Content，再改 `Tex` |

## 6. `SK_Hero` 为什么有两个材质槽

现在两个槽挂的是**同一个**实例，所以看起来「两个元素都一样」。

| 槽 | 名字 | 挂的材质 |
|---|---|---|
| 0 | `blinn3_002` | `MI_HeroSkin` |
| 1 | `pasted__blinn3_002` | `MI_HeroSkin` |

`pasted__` 是 Maya 粘贴材质时自动加的前缀。导出 FBX 时，**每个不同的材质名都会变成一个槽**，哪怕两套 shader 长得一样、扫的是同一张图。

美术那份 `SKM_zhujue` 也是两个槽：`blinn3` 和 `pasted__blinn3`，包围盒与 `SK_Hero` 一样。说明源模型就有两块面被分到两个材质名上，不是导入时多造的。

以后：

- 全身换一张皮：只改 `MI_HeroSkin` 的 `Tex`
- 想某块零件不同：槽 1 另挂一个实例

不必为了好看去删槽。合并槽要回 DCC 重指定材质再导出，收益很小。

## 7. `SK_Hero` 和 `SK_Hero_Skeleton`

**网格是带皮的人；骨架是骨头花名册。** 你在骨架编辑器里看到的皮肤，是预览借了网格，不是骨架自己存了一套贴图。

| | `SK_Hero` | `SK_Hero_Skeleton` |
|---|---|---|
| 类型 | Skeletal Mesh | Skeleton |
| 是什么 | 顶点、三角面、UV、材质槽 | 53 根骨头的名字和父子关系 |
| 管外观 | 管。槽上挂 `MI_HeroSkin` | **不管。** 没有材质槽，也没有 `Tex` |
| 管动画 | 被骨头拖着变形 | 动画、ABP 都绑在这份骨架上 |

`SK_Hero` 记录着「我用哪份骨架」：`SK_Hero_Skeleton`。  
骨架依赖里反过来记着预览网格：`SK_Hero`。  
`ABP_NightHero` 和 Jump / Slash / Sitting 引用的都是 **Skeleton**。换皮改网格材质即可，动画不用重导。

骨架上还有 `KnifeSocket`，挂在 `RightHand`，和贴图无关。

打开 `SK_Hero_Skeleton` 时，预览窗口会拉一份兼容网格（这里就是 `SK_Hero`）画出来，好让你看见骨头在身体里的位置。所以你会看到皮肤——那是**预览**。在骨架窗口里改预览网格，只影响编辑器好看不好看，不会改游戏里角色的材质。

骨架**不能凭空 Add**。没有骨骼网格导入，就不会有这份 `SK_Hero_Skeleton`。`ABP_NightHero` 的 Target Skeleton 建完即固定；美术那个 `ABP_zhujue` 绑的是 `SK_zhujueSitting_Skeleton`，装不到我们主角上。

## 8. `SK_Hero` / 骨架是怎么建出来的

**不是在编辑器里「新建 Skeleton / 新建 Skeletal Mesh」。**  
是同一次 FBX 导入自动拆出网格 + 骨架，再改成现在的名字。换贴图是后面另做的，没有重建这两份。

### 8.1 源文件

当时放在 Content 外面（避免拖进 Content 触发自动导入弹窗）：

`ArtSubmit/Character/mini_zhujue/anim/`

| 文件 | 导入角色 |
|---|---|
| **`Slash_fast.fbx`** | **主文件**：建网格 + 最宽的 53 骨骨架 |
| `Slash.fbx` | 仅动画（常速斩；中间坏过，后有修复版） |
| `Jump_noknife2.fbx` / `_fast` | 仅动画 |
| `Sitting.fbx` | 仅动画（现作占位 idle） |
| `Knife.fbx` | 静态网格（刀），不是角色骨架 |

选 `Slash_fast` 当主文件，因为它骨骼最多（53，多出来的是 `_end_end` 叶尖垃圾骨）。`Jump` / `Sitting` 是同一套 Mixamo 层级的子集（47/48 骨）。先建最宽的骨架，后面的动画才能挂上去。

每个文件单独「网格+动画」一起导，UE 会给每个 FBX 各造一套骨架，跳和砍就无法挂在同一个角色上。S 当初的 `/Game/Art/` 就是这样废掉的。

`ArtSubmit/Character/` 现在可能只剩说明（`.gitkeep`）。游戏用的是已经导好的 `Content/Night/Character/`。要重跑脚本，先把 `mini_zhujue/anim/*.fbx` 放回上面那个目录。新交付先跑 `Tools/ValidateArtFbx.py`（查页脚填充、关键帧是否被整表压缩）。

### 8.2 导入时引擎自动拆什么

| 引擎自动生成（名字多半跟 FBX 走） | 我们改成的名字 | 里面是什么 |
|---|---|---|
| 一份 Skeletal Mesh | **`SK_Hero`** | 皮 + UV + 槽，并记下用哪份骨架 |
| 一份 Skeleton | **`SK_Hero_Skeleton`** | 53 根骨 |

然后其它 FBX **只导动画**，并显式指定这套骨架。刀另导成静态网格。后来在 `RightHand` 上加了 `KnifeSocket`。

### 8.3 控制台跑脚本（当初真实顺序）

编辑器已起、Python 可用。控制台把**相对路径**解析到引擎 `Binaries`，不是项目目录，必须写**绝对路径**。

从 Python 同步调 `ImportAssetTasks` 时，若 Interchange 的 FBX 通道开着，会和老的 `FbxImportUI` 打架，编辑器在任务图上递归等自己 → 崩溃。手搓导入 Blender 动画时，开着 Interchange 还会让人躺着（见 [§10](#10-interchange-和老导入器为什么关掉-fbx-通道人就站了)）。所以必须先关再跑：

```
Interchange.FeatureFlags.Import.FBX 0
py "D:/myProject/MiniGame/MiniGame/Tools/ImportHeroRig.py"
Interchange.FeatureFlags.Import.FBX 1
```

（把盘符改成你本机仓库路径。脚本在 `MiniGame/Tools/`，源目录按脚本写的是再上两级到仓库根下的 `ArtSubmit/...`。）

崩溃重启后若弹出标题为「恢复」的资产恢复框，它是模态的，外部工具会像死了一样。先关掉这个框。

脚本自己的顺序（`main()`）：

1. 检查 `ArtSubmit/Character/mini_zhujue/anim/` 在不在
2. 确保 `/Game/Night/Character` 目录存在
3. **`import_master()`**
   - 若 `SK_Hero_Skeleton` 已存在：直接复用（保住 Socket）
   - 否则：只导 `Slash_fast.fbx` 的**网格**（`import_mesh=true`，`import_animations=false`，材质/贴图开）
   - 验收：该目录下必须正好 1 网格 + 1 骨架
   - 重命名为 `SK_Hero` / `SK_Hero_Skeleton`
4. 清空 `/Game/Night/Character/Anims/` 里旧的 AnimSequence
5. 按列表**仅动画**导入：`Slash_fast` → `Slash` → `Jump_noknife2` → `_fast` → `Sitting`，全部 `options.skeleton = SK_Hero_Skeleton`，材质贴图关
6. 动画导入绕 X 转 **90°**（`ANIM_IMPORT_ROLL`）。Blender 的 Armature 带 −90° X；网格导入会把这旋转烤进绑定姿势（人是站的），只导动画时髋部位在 Armature 本地空间（人是躺的）。`convert_scene` 盖不住这件事
7. 导 `Knife.fbx` 为静态网格
8. 保存目录
9. 验收：骨架数必须 = 1；每条动画髋部在 +Z（站着）而不是 +Y（躺着）；抽样骨骼位移/旋转幅度 ≥ 0.5（空动画会被抓出来）

主网格导入选项对照（`master_options`）：

| 选项 | 值 | 含义 |
|---|---|---|
| `import_mesh` | true | 要人 |
| `import_as_skeletal` | true | 骨骼网格，不是静态模 |
| `import_animations` | **false** | 网格这次不要动画；动画另走一遍，保证同一套代码路径 |
| `import_materials` / `import_textures` | true（仅这一次） | 后面的文件必须关，否则每个 FBX 复制一份材质 |
| `create_physics_asset` | false | 不要 Ragdoll 资产 |

仅动画选项对照（`anim_options`）：

| 选项 | 值 | 含义 |
|---|---|---|
| `import_mesh` | **false** | 不要第二个人 |
| `import_animations` | true | 只要 clip |
| `import_materials` / `import_textures` | **false** | 不要材质副本 |
| `skeleton` | 已有的 `SK_Hero_Skeleton` | **防止再造一套骨架** |
| `import_rotation.roll` | 90 | 见上，站起来 |

三条铁律（和脚本注释一致）：

1. **一套骨架只建一次**；其余文件显式指定这套骨架。
2. 只要动画的文件勾「仅导入动画」。**不要**只关「导入骨骼网格体」——那会把整条骨骼管线一起关，引擎判定没东西可导直接失败。
3. 材质纹理只在第一个文件开，之后全关。

### 8.4 编辑器手搓的等价步骤

不跑脚本时，按这个顺序点，结果应与上面一致：

1. Content Browser 进 `Night/Character`
2. 把 `Slash_fast.fbx` 拖进去（或 Import）
3. 导入窗口选 **Skeletal Mesh**
   - 导入网格：**开**
   - 导入动画：**关**
   - 导入材质/贴图：开（仅这一次）
   - 不要建 Physics Asset
4. 导入后出现网格 + 骨架（名字大概叫 `Slash_fast` / `Slash_fast_Skeleton`）
5. 重命名成 `SK_Hero` / `SK_Hero_Skeleton`
6. 再拖 `Jump_noknife2.fbx`（以及列表里其它动画 FBX）
   - 类型选 **Animation**
   - Skeleton 填 **`SK_Hero_Skeleton`**
   - 不要再导网格、不要导材质
   - 动画导入旋转 X = 90°（否则躺着播）
7. `Knife.fbx` 按 Static Mesh 导
8. 打开骨架，在 `RightHand` 上加 Socket，命名 `KnifeSocket`（如果还没有）
9. 换皮按 §4，与导入无关

不要每个 FBX 都「网格+动画」一起导。

## 9. uasset 和 fbx，`新建文件夹` 为什么必须留那一层

### 9.1 两种文件

| | `.fbx` / `.png` | `.uasset` |
|---|---|---|
| 是什么 | 建模软件 / 画图软件的**源文件** | 引擎里已经导入、编好引用的**资产包** |
| 谁能直接用 | 只能走 Import，生成新的 uasset | 放在 `Content/` 下引擎就能扫到 |
| 引用怎么写 | 没有 `/Game/...` | 内部全是绝对路径，如 `/Game/新建文件夹/模型和材质/贴图/T_zhujue1` |
| 能不能点 Import | 能 | **不能。** Import 对话框选不中 uasset |

`新建文件夹` 下那些 uasset 是美术工程里已经导入好的成品（从 `ArtSubmit/_incoming` 按原目录拷进来）。所以路径必须是 `/Game/新建文件夹/...`。少一层，`MI_zhujue` 就找不到 `M_muban` / `T_zhujue1`，模型变灰块。

FBX 适合「我们自己导、自己起名」。uasset 适合「已经在 UE 里调好的材质/模型，整包迁过来」。uasset **不能**当 FBX 那样 Import，也不能和别人的同名 uasset 做文本合并。

正路只有两条：

1. 让美术在他们工程里 **Migrate**（自动带齐依赖并重写引用）
2. 我们拿源文件自己导（命名和目录可控）

不要直接拷零散 `.uasset` 却改文件夹名。还会把重定向器、`BP_ThirdPersonGameMode` 这类模板遗留物一起带进来。

### 9.2 `_incoming` 预览时的纪律（第 32 轮）

拷贝对应关系：

```
_incoming/关卡        -> Content/新建文件夹/关卡
_incoming/模型和材质  -> Content/新建文件夹/模型和材质
_incoming/蓝图        -> Content/新建文件夹/蓝图
```

| 部分 | 结论 |
|---|---|
| 模型和材质 | 链是全的：`SKM_zhujue` → `MI_zhujue` → `M_muban` → `T_zhujue1` |
| 关卡 | 空的（开了 OFPA，actor 在 `__ExternalActors__`，交付里没有） |
| 蓝图 | 引用第三人称模板的 `IA_Move` 等，和「只有跳/砍」冲突，不能当夜关 Pawn |

成对出现的几 KB 文件常常是 `ObjectRedirector`（重命名残留），例如 `T_zhujue` → `T_zhujue1`。

中文路径在 uasset 里按 UTF-16 存。用 ASCII 扫 `/Game/` 会漏掉，误以为没有互相引用。

### 9.3 和主角换皮怎么叠在一起

我们现在的主角是：

- **FBX 网格**（`SK_Hero`，自己导、自己起名）
- **uasset 母材质**（`M_muban`，留在 `新建文件夹` 原路径，因为引用写死了）
- **我们自己的贴图 + 实例**（`T_HeroSkin` / `MI_HeroSkin`，放在 `Night/Character`，不直接引用未跟踪的 `T_zhujue1`）

所以会看到：`MI_HeroSkin` 的 Parent 仍指向 `/Game/新建文件夹/.../M_muban`。删掉或改名 `新建文件夹`，皮肤实例会断母材质。

## 10. Interchange 和老导入器：为什么关掉 FBX 通道人就站了

**短答：这句话是在换门。默认走新门（Interchange），Blender 只导动画时不会把人转正；关掉后走老门，轨道会按已经站着的 `SK_Hero_Skeleton` 重算。**

### 10.1 引擎里有两扇门

UE 5.8 导入 FBX 可以走两条路：

| | 新门（默认开） | 老门 |
|---|---|---|
| 名字 | Interchange | 旧 FBX 导入器（`FbxImportUI`） |
| 你看到的窗口 | 分页的「导入内容」，上面一排 Common / Mesh / Animation | 老式一整页勾选 |
| 谁决定走哪扇 | 控制台变量 `Interchange.FeatureFlags.Import.FBX` | 把它设成 `0` 就改走老门 |

`1`（默认）= 所有 FBX 进 Interchange。  
`0` = 暂时别让 Interchange 碰 FBX，改走老导入器。  
这是**编辑器本次运行**的开关，不是改项目文件；导完应打回 `1`，免得以后导普通模型也绕开新管线。

### 10.2 为什么新门会躺着

Blender 导出时，Armature 节点自己带着 **−90° X**（它的 Z-up 转成 FBX 的 Y-up）。

- **导网格**：引擎把这旋转**烤进绑定姿势**。所以 `SK_Hero` 是站着的，骨架也是站着的。
- **只导动画**：新门几乎是按 FBX 里 Armature 的本地空间，把髋部轨道抄进来。身高落在 **Y** 上，人就躺着跳 / 躺着呼吸。
- 你在 Common 里填的 **Offset Rotation = 90°** 是给网格/组件用的，**动画轨道不吃**。所以填了也躺。

量髋部就能看出来（相对父骨）：

| 片子 | 身高轴 | 判定 |
|---|---|---|
| Interchange 导的 `Jump` | Y：57 → 143 → 57，Z 钉在 −1.23 | 躺着 |
| 老门导的 `Idle_Breath` / `Jump_noknife2` | Z 起伏，Y 几乎不动 | 站着 |

动作幅度可以是对的（真的在跳），只是整个人躺在地上做这个动作。不是头朝下倒立。

依赖也能当记号：还走新门的片子会挂 `/Script/InterchangeEngine`；呼吸你重新导入站起来之后，这条依赖就没了。

### 10.3 为什么老门会站着

老导入器对**动画**有单独的「导入旋转 / Convert Scene」，会按**目标骨架的空间**重算轨道。`SK_Hero_Skeleton` 的绑定姿势已经是站着的（第 19 轮导网格时烤过那 90°）。所以关掉新门再导，等于把片子装进已经站着的那套骨头里，不必再手填 Offset。

`Tools/ImportHeroRig.py` 当初就是给老门写的：先 `Import.FBX 0`，再设 `import_rotation.roll = 90`，导完再开回去。手搓时「关通道 + 指定 `SK_Hero_Skeleton` + 清掉不属于这套骨架的栈」就是同一条路。

### 10.4 清掉「该骨骼不会有的动画」算哪一步

`Jump101.fbx` / `Breath101.fbx` 里几十上百条 Action，绝大多数在动 Camera、Light、多余叶尖骨。UE 会提示这些不属于 `SK_Hero_Skeleton`。清掉它们，剩下的才是能挂上的那一条真动作。

清垃圾**不会**单独把躺着的轨道转正；它只是让「装进现成骨架」能干净跑完。真正转正的是**换门 + 绑到站立骨架**。

### 10.5 手搓时怎么用

```
Interchange.FeatureFlags.Import.FBX 0
```

然后右键已有片子 → **重新导入**（或把 FBX 拖进 `Night/Character/Anims`）：

- 骨架填 `SK_Hero_Skeleton`
- 仅导入动画
- 清掉不属于这套骨架的栈 / 骨头
- 预览：身高应沿 **Z** 走

导完：

```
Interchange.FeatureFlags.Import.FBX 1
```

`Idle_Breath`、`Jump` 都按这套站起来。以后这批 Blender 动画不要用默认的 Interchange 分页窗硬导。

## 附录 A：曾经灰掉的两种原因（避免再踩）

1. **图集错了**（第 28 轮）：槽铺满了，但铺的是 kat 的 `T_Hero` / `T_HeroBase`。UV 对不上。
2. **运行时又盖回去了**（第 33 轮）：资产已经换成 `MI_HeroSkin`，但编辑器跑的是旧 DLL，`ApplyHeroMaterial` 仍用 `HeroMaterial`（`MI_HeroTexture`）逐槽覆盖。源码已删这行，Live Coding 补丁在重启后消失，必须整编。看 PIE 里 `HeroSkelMesh.OverrideMaterials` 是否又变成 `MID_MI_HeroTexture_*`。

材质属于**网格槽**，不属于「角色身上一个 HeroMaterial 配置」。静态模和骨骼模槽数不同、UV 也不同。
